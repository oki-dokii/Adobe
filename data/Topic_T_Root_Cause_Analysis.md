## 0. Framing — what Topic T is actually for

Topic T is not "trace symptoms back to one cause" as trivia. It exists to answer one design question for the marketplace:

> **Given a set of independently-generated findings from multiple detection skills (crawlability, rendering, entity identity, corroboration, cross-web consistency, content structure, engagement), can an orchestration layer correctly determine which findings share a common underlying explanation and should be merged into one diagnosis — without either (a) falsely collapsing genuinely independent problems into one overstated narrative, or (b) reporting a symptom as if it were the cause when the honest, evidence-backed answer is that several independent factors are each necessary but only jointly sufficient to explain what was observed?**

This framing is deliberately more cautious than "find the root cause," and that caution is itself this document's central, evidence-backed finding — see §1.

Unlike Topics F, H, P, and M, Topic T is not primarily a website-signal-detection topic. As Pulkit's own Topic A document explicitly notes at several points (A19, A22), root-cause aggregation is fundamentally **orchestrator logic** — reasoning applied to findings other skills already produced, not a new class of on-page signal to crawl for. This document is organized accordingly: rather than six A–O investigation units modeling distinct website signals, it has **two investigation units modeling the aggregation logic itself**, plus a **worked synthesis section** applying that logic to the actual finding inventory this document series (Topics F, H, P, M) and Pulkit's Topic A have already produced — since T's job is specifically to operate on that accumulated inventory, not to invent a new one.

1. **§1 — Is "root cause" even the right model?** What does the actual evidence say about single-linear-cause reasoning's reliability, and what should replace or refine it for this specific, more constrained problem (a one-shot website audit, not a live incident investigation)?
2. **§2 — Mechanics of correct aggregation:** given §1's answer, what concrete, implementable logic determines when two findings from different skills should be merged, and what should the resulting output structure look like?
3. **§3 — Worked application:** applying §1/§2's logic to the actual findings this document series has already produced (Topics F, H, P, M, and Pulkit's Topic A), as a concrete demonstration and stress-test of the design, per the brief's own explicit worked example (JS-only pricing → chain of downstream effects).

**Constraint from the handout, re-read carefully:** the brief's own worked example is explicit: "Your skill shouldn't output five unrelated observations when there is one underlying cause." This is the brief's own stated ideal, and it is genuinely well-supported by *some* of the evidence in §1 — but the same evidence base also shows this ideal can be taken too literally, producing a different, opposite failure mode (false-single-cause reductionism) that is at least as well-documented a risk as the "five unrelated observations" problem the brief warns against. Both failure modes are real; T's job is to navigate between them, not to over-correct toward either.

## 1. FACT vs OBSERVATION vs HYPOTHESIS vs INFERENCE vs SPECULATION — global legend

Same legend as Topics F, H, P, and M, used identically here:
- **FACT** — documented by the vendor/standards body, or established in peer-reviewed/archival literature.
- **OBSERVATION** — reported by independent researchers/practitioners running real, methodologically transparent trials (not vendor-confirmed).
- **HYPOTHESIS** — our proposed testable claim, not yet validated by us.
- **INFERENCE** — reasonable derivation from FACT/OBSERVATION, one logical step removed.
- **SPECULATION** — plausible but unconfirmed; flagged, not built on.

**A note on source quality control and an important methodological pivot, continuing the pattern established in Topics F, H, P, and M.** My first research pass for this topic searched the industrial/process-engineering root-cause-analysis literature (fault trees, causal digraphs, Bayesian-network-based alarm correlation, Granger-causality methods for chemical/nuclear/telecom fault diagnosis). This literature is real, rigorous, and peer-reviewed — but, on reflection, it is a poor mechanistic match for this hackathon's actual problem: it is built for **continuous, quantitative, time-series sensor data** in **physical/industrial systems** with **known causal topology** (a piping diagram, a network graph), diagnosed via statistical/probabilistic inference over streams of numeric readings. A website audit's findings are **discrete, mostly symbolic, one-shot, and heterogeneous in kind** (a crawl-rendering delta is not the same kind of object as an entity-collision risk score) — closer in shape to **software incident postmortem analysis** (diagnosing a single discrete failure from heterogeneous, qualitative evidence — logs, configuration state, human actions) than to industrial fault-tree diagnosis. I explicitly changed research direction based on this mismatch rather than force-fitting the industrial literature's specific techniques (Bayesian networks, Granger causality) into a context where their actual mathematical prerequisites (continuous time-series data, known network topology) don't hold — this pivot is itself a small, worth-stating instance of the evidence-hierarchy discipline this document series has applied throughout: matching evidence to the actual shape of the problem, not merely to the presence of the word "root cause" in a search result.

## §1 — Is "root cause" even the right model?

### A. What we need to understand
The brief explicitly asks for root-cause reasoning and gives a worked linear example (JS-only pricing → cascading downstream effects). Is a single, linear, "one true root cause" model the correct target for this marketplace to aim for, or does the best available evidence on causal reasoning in complex systems suggest a different, more defensible target?

### B. Why it matters for the hackathon
Getting this wrong in either direction is costly. If T's design assumes every set of related findings collapses to one true root cause, it will — per the evidence below — sometimes produce a **false, oversimplified narrative** that misdirects remediation effort (fixing the "identified" cause without addressing genuinely independent contributing factors that remain). If T's design instead treats every finding as fully independent, it reproduces exactly the "five unrelated observations" failure the brief explicitly names as the problem to avoid. The evidence in this section exists to find the genuinely defensible middle path, not to pick one extreme.

### C. Current evidence
- **FACT/OBSERVATION, foundational, directly on point, the single most load-bearing finding in this entire topic:** John Allspaw (then head of engineering at Etsy, drawing directly on the peer-reviewed resilience-engineering literature of Richard Cook, Erik Hollnagel, David Woods, and Sidney Dekker) articulates a well-established, extensively cited critique in complex-systems safety engineering: **"there is no root cause"** for failures in complex socio-technical systems — instead, failures emerge from **multiple contributing conditions, each necessary but only jointly sufficient** to produce the observed outcome (a formulation directly quoting Hollnagel, Woods, Dekker & Cook's introduction to *Resilience Engineering*, itself a genuine academic text, not informal commentary). This is not a fringe or purely rhetorical position — it is a mainstream position within the resilience-engineering and safety-science research tradition, with James Reason's well-known "Swiss Cheese" model of accident causation cited as a related, though still partially limited, attempt to move past strict single-cause linear thinking.
- **FACT/OBSERVATION, directly on point, on the specific mechanism popular tools get wrong:** the well-known "5 Whys" technique — the most common practical implementation of linear root-cause reasoning in industry — is widely, consistently documented across independent practitioner and safety-literature sources as resting on a specific, named, flawed assumption: that **"each presenting symptom has only one sufficient cause."** Documented limitations, converging across multiple independent sources (SafetyCulture's practitioner guide, RCA-focused consultancy content, and the more rigorous Allspaw/Cook lineage) include: the method's results depend heavily on facilitator skill/bias (an analog risk for this marketplace would be over-reliance on a single LLM-escalation judgment call without cross-checking); it is not idempotent (different runs/framings can produce different "root causes" for the same underlying situation); and it structurally cannot surface cases where multiple factors are each independently necessary — the method's own linear chain-following structure forces a single-path narrative even when the truth is a joint-sufficiency structure.
- **FACT, directly relevant, on a genuinely important nuance this document must not overstate:** the same source material is explicit that rejecting single-root-cause thinking does **not** mean rejecting causal-chain reasoning as valueless — Allspaw explicitly states "I'm not specifically knocking the Five Whys as a practice with no value, just that it's limited in its ability to identify items that can help bring resilience to a system," and separately notes that a mature, open process of investigating causality using *any* structured model is valuable. This is an important, honest distinction to preserve: the evidence argues against **false confidence in a single, linear, complete explanation**, not against causal-chain reasoning as a technique per se — the brief's own JS-pricing worked example remains a perfectly legitimate use of chain reasoning; the risk is treating every situation as if it necessarily has that same clean, single-path shape.
- **INFERENCE, an important scoping distinction this document must make explicitly:** the cited resilience-engineering literature is developed specifically for investigating **complex, emergent, socio-technical accidents** (aircraft crashes, industrial disasters, major outages) involving human decision-making, organizational pressures, and genuinely unpredictable interaction effects — a considerably higher-complexity domain than this hackathon's actual task (diagnosing why an AI system might fail to find/correctly represent a website, from a fixed, bounded, mostly-technical set of possible causes: crawl blocks, rendering gaps, entity ambiguity, staleness, corroboration gaps, structural issues). **This document is not claiming website-audit root-cause reasoning is exactly as intractable as aircraft-accident investigation** — that would be a mismatched-domain overclaim of exactly the kind this document series consistently flags and avoids. The defensible, scoped claim is narrower: the same **underlying logical structure** (a symptom can have multiple, independently-necessary contributing factors, not always one true single cause) applies here too, at a smaller scale and with a much more bounded, enumerable set of candidate causes than a real-world accident investigation — meaning the *caution* generalizes even though the *complexity level* does not.
- **HYPOTHESIS (ours), the practical design conclusion this section supports:** T's aggregation logic should default to a **"contributing factors, jointly weighted" model** rather than a **"single identified root cause" model** — reporting, for a cluster of related findings, the set of factors that together explain the observed symptom(s), each labeled with its individual evidential strength and its logical relationship to the others (necessary-and-sufficient-alone vs. necessary-but-only-jointly-sufficient vs. merely-correlated-not-causally-linked) — rather than forcing every cluster into a single-line "the root cause is X" verdict. This is a more defensible, more honest, and — per the evidence above — more likely to be *actually correct* target than the brief's literal single-root-cause framing would produce if followed too rigidly, while still fully satisfying the brief's actual underlying goal (don't report unrelated scattered symptoms) whenever a genuine single dominant cause *does* exist, which — per §3's worked application below — is often the case for the more mechanically bounded failure types this marketplace's other skills actually detect.

### D. Important mechanisms
The central tension this unit resolves: the brief's worked example (JS-pricing → cascading effects) is a genuine, valid instance of clean linear causation, and this document series' own prior topics have already produced several comparably clean chains (see §3). But the same prior topics have *also* already produced findings that are explicitly **not** reducible to a single upstream cause — e.g., Topic F's F47-F50 (a post-merger identity gap compounds *three separate* mechanisms — aliasing, topology, and collision risk — simultaneously, none of which is "the" cause of the others) is this document series' own existing, concrete illustration of the "each necessary, only jointly sufficient" pattern, already present in the accumulated finding inventory before this topic document was even written. T's design must handle **both** shapes correctly, defaulting to neither.

### E–G. (Signals / Detection / Evidence — reframed for this orchestrator-logic unit)
Because this unit produces reasoning-design guidance rather than a website signal, its "signal," "detection," and "evidence output" are the **classification test** applied to any two-or-more findings before merging them: for a candidate pair/cluster of findings, ask (1) does removing the *effect* of only one of the findings, hypothetically, fully explain the absence of the other symptoms (single-sufficient-cause structure — merge into one linear diagnosis), or (2) would the symptoms persist unless *all* the candidate factors were addressed (jointly-necessary structure — report as a connected-but-multi-factor diagnosis, not a single line item)? This binary test, applied per-cluster, is this unit's actual deliverable.

### H. Possible severity logic
Not directly applicable to this unit alone — severity logic is addressed in §2 (aggregation mechanics) and depends on this unit's classification output (single-cause clusters get one severity rating derived from the worst affected symptom; jointly-necessary clusters should report a combined severity that doesn't understate the problem by fragmenting it, but also doesn't overstate confidence in any single factor's fix resolving everything).

### I. Correct remediation
For single-sufficient-cause clusters: remediate the one identified cause (matching the brief's own worked-example framing exactly). For jointly-necessary clusters: remediation guidance must explicitly list all contributing factors and state that addressing only a subset is expected to be insufficient — an honest, evidence-backed departure from the false reassurance a forced single-cause narrative would otherwise imply.

### J. False-positive cases
The most significant false-positive risk this unit exists to prevent: **over-merging** distinct, independently-caused findings into a false single narrative because they happen to co-occur or are topically adjacent, when they are not actually causally linked at all (a genuine risk explicitly flagged in Pulkit's own Topic A A22 discussion of template-clustering, and directly relevant here) — the classification test in §E-G is specifically designed to require an actual causal argument (would removing X explain the absence of Y), not mere topical proximity, before merging.

### K. False-negative risks
The opposite, equally real risk: **under-merging**, reporting genuinely connected findings as unrelated because the causal link between them isn't obvious from a surface reading (exactly the failure the brief's worked example warns against) — this is why the classification test must be actively applied to every plausible pair of findings touching the same page/entity/claim, not left to chance discovery.

### L. Counterexamples
Two findings that are statistically or topically correlated across many audited sites in general (e.g., sites with JS-locked pricing also frequently have thin entity disambiguation, for unrelated reasons — perhaps both simply correlate with "less mature web engineering practice" generally) should **not** be merged into a claimed causal relationship for any *specific* site's audit unless the specific-site evidence actually supports it — this is a direct, specific application of the brief's own "never assume correlation means causation" instruction to T's own core task, and is arguably the single place in the entire marketplace where that instruction is most directly operative.

### M. Does this generalize across site types?
Yes — the classification logic (single-sufficient vs. jointly-necessary) is a general reasoning pattern, not tied to any specific site type; what varies by site type is *which* specific findings are likely to cluster together (a hook to Topic V, consistent with every other topic in this series).

### N. Candidate skill(s)
Not a detection skill — this is core **orchestrator/entrypoint logic**, consistent with how Pulkit's own Topic A document (A19, A22) already frames comparable aggregation questions as belonging to the entrypoint rather than to any individual skill.

### O. Relationship to other potential skills
Directly and centrally relevant to Topic S (Scoring & Severity, Soham's assignment per the distribution sheet) — the classification output this unit produces (single-cause vs. jointly-necessary) must be a first-class input to whatever severity/confidence schema Topic S designs, not an afterthought; this is the most consequential cross-reference in this entire document and is elevated to the top of §4 below.

## §2 — Mechanics of correct aggregation

### A. What we need to understand
Given §1's classification logic, what concrete, implementable structure should the aggregation process actually follow — what does a finding need to carry to make it mergeable at all, what triggers a merge attempt, and what does correctly-aggregated output look like?

### B. Why it matters
§1 establishes the *test* for whether findings should merge; this unit establishes the *mechanism* that applies that test systematically across a full audit's finding set, rather than relying on ad hoc, one-off reasoning per audit run — a mechanism is what makes this reproducible and implementable within the hackathon's constraints, not merely a philosophical position.

### C. Current evidence
- **INFERENCE, built primarily from this document series' own accumulated design decisions rather than a single new external source (consistent with Topic P's §2, which made a comparable move for materiality classification):** no external source found in either research pass proposes a ready-made aggregation-mechanics framework specifically suited to a one-shot, heterogeneous, multi-skill website-audit context — the industrial RCA literature's mechanisms (Bayesian network structure learning, Granger causality) require data types this problem doesn't have (continuous time series), and the software-incident-postmortem literature's mechanisms (Allspaw's own recommended practice) are designed for *retrospective human investigation with interview data*, not *automated, single-pass symbolic aggregation of heterogeneous machine-generated findings*. This unit is therefore, like Topic P §2, explicitly labeled HYPOTHESIS-tier original synthesis — informed by but not directly copied from either literature, adapted to this problem's actual constraints.
- **HYPOTHESIS (ours), the core mergeability precondition, directly building on infrastructure this document series has already established:** two findings should only be considered for merging if they share at least one of: (a) the same specific page/URL, (b) the same specific entity/claim (reusing the claim-identification infrastructure already established in Topic P §2's materiality taxonomy), or (c) an explicitly-documented causal-mechanism link already established in this research series' own findings (e.g., Topic F's own cross-reference notes, or Pulkit's Topic A's explicit chain, JS-rendering → extraction failure → source substitution). This precondition is what prevents the over-merging false-positive risk named in §1 J — topical similarity alone (e.g., "both findings are about trust") is explicitly **not** sufficient grounds for a merge attempt; a concrete shared anchor (same page, same entity, same claim, or a documented mechanism link) is required.
- **HYPOTHESIS (ours), the merge-or-cluster decision, directly applying §1's classification test:** once two-or-more findings share a mergeability precondition, apply §1's binary test (would removing the effect of one candidate finding explain the absence of the others). If yes for all but one — merge into a single linear diagnosis, naming that one factor as the identified cause (satisfying the brief's own worked-example framing exactly, for the cases where it genuinely applies). If the symptoms would persist without addressing multiple factors jointly — report as a **connected cluster**, not a single line item and not scattered unrelated findings either: one heading, multiple explicitly-labeled contributing factors, combined severity, and remediation guidance naming all required fixes.
- **HYPOTHESIS (ours), directly reusing the confidence-labeling practice this document series has established independently in multiple prior topics (Topic P §3's platform-confidence labels; Topic M's Finding M-03 dual-confidence rating):** every merge or cluster decision should itself carry an explicit confidence label (high: a documented, well-evidenced mechanism link exists per this research series' own findings; medium: a plausible but not directly evidenced inferential link; low: co-occurrence noted but causal link uncertain) — directly extending, not inventing anew, a discipline this document series has already applied consistently, now formalized as T's own core deliverable rather than a per-topic aside.

### D. Important mechanisms
The mergeability-precondition + binary-classification-test + confidence-labeling structure together form a **conservative-by-design aggregation pipeline**: it requires positive evidence of a shared anchor and a genuine causal argument before merging anything, and it always preserves and reports uncertainty explicitly rather than collapsing it into false confidence — directly implementing §1's core finding (avoid both under-merging and false-confidence over-merging) as an actual, checkable procedure rather than a general principle left to per-audit judgment.

### E. Concrete "signals" (procedure inputs)
Every individual finding entering this pipeline must already carry, at minimum: the specific page/URL and/or entity/claim it concerns (already a standing requirement across this document series' finding-register format), and — where applicable — a reference to any documented mechanism link from the source topic's own research (e.g., Topic F's own F17-F50 cross-references, or this document series' repeated practice of explicitly flagging relationships between findings in each topic's own §4).

### F. How the procedure would run
Deterministic-first: index all findings by page/entity/claim; for any group sharing an anchor, run the binary classification test — this can often be answered deterministically from the findings' own already-documented mechanism relationships (many of which this document series has already pre-computed across Topics F, H, P, M — see §3) rather than requiring fresh LLM reasoning per audit. Escalate to a single LLM judgment only for genuinely novel finding combinations not already covered by a documented mechanism link in the research base — a legitimate, bounded hybrid-approach use, consistent with this document series' standing discipline, and importantly a much *smaller* LLM-reasoning burden than a naive "have an LLM figure out the root cause" approach would require, since much of the mechanism-mapping work is already done by this research phase rather than needing to be inferred live at audit time.

### G. What evidence the orchestrator should report
For each cluster: the anchor (page/entity/claim), the classification (single-cause vs. jointly-necessary), each contributing finding with its own individual evidence/confidence (inherited from its source skill), the cluster's own merge-confidence label, combined severity, and remediation guidance addressing all necessary factors — never a bare, unlabeled "root cause: X" line that hides the underlying uncertainty or joint-sufficiency structure.

### H. Possible severity logic
Cluster severity should not simply average or sum the individual findings' severities (which could either dilute a genuinely critical joint-cause situation or overstate a loosely-related cluster) — it should be derived from the **worst-affected downstream symptom**, consistent with how severity is scoped in every individual topic in this series (e.g., Topic F's F41-F46 severity is driven by the misattribution risk, not by counting sub-signals), with an explicit modifier noting whether the fix requires one action (single-cause) or several jointly (jointly-necessary) — this modifier itself should factor into remediation *effort* estimation (a Topic S concern) separately from severity/impact.

### I. Correct remediation
Directly follows from the classification: single line-item for single-cause clusters (satisfying the brief's actual worked example); an explicit, complete list for jointly-necessary clusters, with a stated warning against partial fixes creating false confidence — this warning is itself a direct, practical translation of Allspaw's own core point (§1 C) into report language a non-expert user can act on correctly.

### J. False-positive cases
A cluster confidently labeled "single-cause" when the true structure is actually jointly-necessary would produce exactly the false-reassurance failure §1 warns about (user fixes the named cause, problem persists, trust in the tool erodes) — this is why the classification step must default toward the more conservative jointly-necessary framing whenever the evidence for full single-sufficiency is not clearly established, rather than defaulting toward the simpler, more satisfying single-cause narrative under ambiguity.

### K. False-negative risks
Overly conservative default-to-jointly-necessary framing, applied indiscriminately, risks reproducing a version of the "big checklist" problem in a new form (long lists of "contributing factors" for situations that actually do have one clear dominant cause) — the mergeability precondition and confidence-labeling requirements (§C) are the specific checks against this, but the calibration between these two failure modes is, like Topic P's materiality taxonomy, explicitly unvalidated design work that should be tested against real cases before the Combine phase finalizes thresholds.

### L. Counterexamples
None beyond those already covered in §1 L (correlation-without-causation across the broader site population must not be imported into any single site's specific cluster analysis).

### M. Does this generalize across site types?
The mechanics generalize universally — they operate on the finding data structure, not on site-specific content — with the caveat (shared with every topic in this series) that which specific findings actually co-occur and what mergeability preconditions they satisfy will vary by site type.

### N. Candidate skill(s)
Not a detection skill — core entrypoint/orchestrator logic, as established in §1 O.

### O. Relationship to other potential skills
The mergeability-precondition design directly depends on every other skill's findings carrying consistent page/entity/claim anchoring — this is a **cross-cutting output-contract requirement** this document recommends be imposed on all skills across the marketplace (a design constraint for Soham's entrypoint/composition work, and for Pulkit's and my own skills alike), not merely a T-specific detail.

## §3 — Worked application: applying the framework to this document series' own accumulated findings

This section is the direct, concrete analog to the brief's own worked JS-pricing example, and the strongest evidence this document can offer that the §1/§2 framework actually works — because, unlike a hypothetical illustration, it is applied here to real findings this research series has already independently produced across four prior topic documents, without those documents having been written with this classification scheme in mind.

**Example A — genuine single-sufficient-cause cluster (validates the brief's own framing, and the design should handle this cleanly):**
Pulkit's Topic A finding A-01 (JS-rendered content is absent from raw HTML, per `crawl-render-audit`) and the brief's own worked appendix example (JS-only pricing → machine cannot extract pricing → AI lacks pricing evidence → third-party pricing source may be selected → user lands on site with expectation mismatch) is a textbook single-sufficient-cause chain: removing the JS-rendering-dependency finding (i.e., server-rendering the pricing content) would plausibly eliminate the entire downstream chain. Classification: **single-cause**. This is the case type the brief's worked example was built around, and this document's framework correctly identifies it as such rather than over-complicating it with unnecessary joint-factor hedging.

**Example B — genuine jointly-necessary cluster, already present in this document series' own prior output before this topic was written:**
Topic F's F47-F50 (multiple domains/M&A/historical identity) explicitly documents a case where **three separate mechanisms compound simultaneously**: an aliasing event (F23-F30 — old company name still in use), a topology change (F18-F19 — the acquired entity becomes a subsidiary), and elevated collision risk (F41-F46). Per F47-F50's own §D: "Detecting and connecting all three compounding effects... is the direct, practical expression of the brief's 'prefer one connected diagnosis over several unrelated findings' instruction, applied within Topic F itself." Testing this against §1's binary classification: would removing only the aliasing factor (e.g., fixing internal name-consistency) fully resolve the identity-resolution risk, if the topology change and collision risk remain unaddressed? No — per F47-F50's own reasoning, each factor is independently capable of causing confusion even if the others were fixed. Classification: **jointly-necessary**. This is a genuine, real (not manufactured) example already sitting in this research series' output, and it directly validates that the §1/§2 framework's jointly-necessary category is not a hypothetical edge case invented to hedge — it is a real structure this research has already, independently encountered.

**Example C — a cross-topic single-sufficient-cause chain spanning two different researchers' work, directly testing the mergeability-precondition mechanism (§2):**
Topic P's Finding P-01 (stale, ambiguously-dated third-party content actively misleads retrieval-based AI systems, per the Temporal Accuracy Gap evidence) and Topic H's §4 provenance findings (contradictory corroboration is a distinct, higher-severity case than simple absence) share an explicit, documented mechanism link (both this document series' own cross-references, and both concern the same underlying "compare claim against external source" shared infrastructure established in Topic P §4). Applying §2's mergeability precondition: do they share an anchor? Yes — both concern the same class of object (a specific, checkable claim) and explicitly reference the same shared comparison infrastructure. Applying §1's classification: if a specific claim is both undated (Topic P §1) *and* has a contradicting third-party source (Topic H §4), is the undated-ness alone sufficient to explain the misattribution risk, or is the external contradiction independently necessary too? Here the honest answer is **the undated claim is a risk-factor/contributing-cause, not independently sufficient on its own** (per Topic P §1 H's own severity logic, which explicitly states undated claims alone are only low-medium severity and "escalate only when combined with an actual cross-source discrepancy") — meaning this is itself a **jointly-necessary** structure, but one where the two factors have asymmetric weight (the contradiction is doing more causal work than the missing date, which is more of an enabling/risk-amplifying condition than a co-equal necessary cause). This surfaces a genuine refinement to §1/§2 worth flagging: **the jointly-necessary category itself may benefit from a further distinction between "co-equal necessary causes" and "a primary cause plus risk-amplifying conditions,"** a nuance neither this document's §1/§2 design nor the source resilience-engineering literature explicitly separates, and which is flagged here as a finding in its own right (see Finding T-03) rather than silently smoothed over.

## 3. Required end-of-topic synthesis

**Strongest validated insight:**
"There is no root cause" (Cook/Hollnagel/Woods/Dekker, operationalized by Allspaw) is a well-established, mainstream position within complex-systems safety engineering, and the popular "5 Whys" technique's core documented weakness — assuming every symptom has exactly one sufficient cause — is a real, named, widely-recognized limitation, not an invented caveat. This directly and materially refines how this marketplace should interpret the brief's own "prefer root causes over symptoms" instruction: the instruction's actual target (don't report scattered, unconnected observations when a real connection exists) is well-supported and should be pursued, but its most literal reading (force every situation into one named root cause) is a documented cognitive shortcut with a real failure mode of its own, and this document's §1/§2 framework is built specifically to capture the brief's genuine intent without inheriting that shortcut's risk.

**Strongest unvalidated hypothesis:**
The three-way classification refinement discovered in §3 Example C / Finding T-03 (single-sufficient / co-equal-jointly-necessary / primary-cause-plus-amplifying-conditions) — a genuinely useful-seeming refinement discovered through actually applying the framework to this document series' own real prior findings, but tested against only one concrete cross-topic example so far, and not yet validated against a broader set of finding combinations.

**Strongest candidate skill:**
None in the traditional sense — this topic's primary deliverable is the aggregation-logic design itself (§1, §2), which should live in the marketplace's single entrypoint/orchestrator rather than as a peer detection skill, consistent with how Pulkit's own Topic A document already anticipated (A19, A22) that comparable aggregation questions belong at the entrypoint level.

Whether the mergeability-precondition and binary/three-way classification mechanics (§2) actually work correctly when applied to the *full* combined finding set once all topics (F, H, P, M, plus Pulkit's and Soham's) are complete — this document's §3 worked application is a real but small-scale test (three examples, drawn only from topics I authored or co-referenced), not a full-system validation.
